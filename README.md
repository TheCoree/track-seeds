# track-seeds

Следит по IP-камерам за двумя семенодробилками и сообщает, когда **семена (сырьё)
заканчиваются**: уведомлением на телефон (ntfy), голосом через динамик (камеры Hikvision
в комнате отдыха или физический динамик у сервера) и тревогой в браузере.

**Дробилки вшиты в программу** (`src/track_seeds/crushers.py`): «Дробилка 1» (камера
192.168.1.239) и «Дробилка 2» (192.168.1.240) — с зонами и эталонами, подобранными по записи
с этих камер. Анализ — по субпотоку 640×360, дважды в секунду: обе дробилки вместе занимают
~10 % одного ядра и ~430 МБ памяти (рассчитано на сервер с 2 ядрами и 4 ГБ). Камера смотрит в открытый желоб под бункером: зона «Желоб» показывает, есть ли
семена, зона «Привод» (цепь со звёздочкой) — работает ли дробилка. Пока дробилка стоит,
о семенах не сообщается.

На месте настраиваются только пароль камеры, оповещения, фразы, динамики и эталоны, снятые
потом. Это лежит в `config/` — в программу не попадает:

```
config/                      CONFIG_DIR
├── settings.json            уведомления, голос (общие для обеих дробилок)
└── crushers/
    ├── drobilka-1/
    │   ├── settings.json    что поменяли в интерфейсе (только отличия от программы, без паролей)
    │   ├── secrets.json     пароли камеры и динамиков (права 600)
    │   └── samples/         эталоны, снятые на месте (вшитые — в src/track_seeds/builtin/)
    └── drobilka-2/
data/                        журнал событий, снимки, кеш голоса, отчёты о работе (worklog.db),
                             аккаунты клиентов (accounts.db, права 600) — создаются на сервере
```

**Две панели на одном сайте.** Разработчик (вы) видит всё: дробилки, настройки, эталоны,
клиентов. Клиент — дробилки в реальном времени, события и отчёты за день / неделю / месяц
(сколько работала, стояла, крутилась без зерна), без настроек, адресов камер и паролей.
Клиент регистрируется сам по одноразовой ссылке, которую выдаёте вы. Сайт ставится на телефон
как приложение (PWA), есть виджет для iPhone (Scriptable).

Прежние пресеты (`config/presets/`) при первом запуске переносятся сами: пароль, оповещения,
динамики и свои эталоны — в `crushers/`, папка `presets/` — в `config/.trash/`.

## 1. Запуск на своём ПК

```bash
make install            # venv + зависимости + .env + npm install
make web                # собрать веб-интерфейс
make serve              # http://127.0.0.1:8080/
```

1. **Дробилка → «Камера»:** пароль камеры → «Проверить подключение» → «Сохранить».
   Без браузера: `track-seeds password` (один пароль для обеих камер).
2. **«Наблюдение»:** живой кадр с зонами, «Семена есть / закончились» с уверенностью в %,
   «Дробилка работает / стоит», графики за 15 минут.
3. **«Оповещения»:** когда сообщать, свои фразы с «▶ Прослушать», куда говорить (динамик
   камеры Hikvision и/или у сервера). **«Проверить оповещение»** прогоняет всю цепочку
   с пометкой «ПРОВЕРКА».
4. **«Эталоны»:** вшиты 4 кадра «семена есть» на каждую дробилку. Когда желоб впервые
   опустеет — в журнале событий «сделать кадр эталоном → пусто» (или «Сейчас пусто» на этой
   вкладке, или кадр из архива регистратора файлом). Ночью при ИК-подсветке — снимите
   ещё «семена есть».
5. **«Уведомления и голос»** (общие): ntfy-топик → «Тест»; голос (сохраняется сразу).
6. **Камера: «Зоны» / «Оригинал»** — переключатель в углу каждого кадра (запоминается в
   браузере). «Зоны» — кадр раз в секунду с зонами и уверенностью; «Оригинал» — видео с
   камеры как есть (субпоток, до 12 к/с, ~2 Мбит/с). Видео идёт, только пока вкладка
   открыта; одновременно — не больше 8 зрителей.

Без `WEB_PASSWORD` на ПК вход не нужен — только с этого компьютера. «Мой аккаунт» → завести
разработчика (или `track-seeds admin`) — дальше вход по логину и паролю.

## 2. Сервер: Lenovo ThinkCentre (2 ядра, 4 ГБ), Docker

Обе дробилки вместе — ~10 % одного ядра и ~400 МБ памяти (анализ по субпотоку 640×360).

**Один раз:**

1. **BIOS** (F1 при включении): *Power → After Power Loss → **Power On*** — после пропадания
   питания сервер включится сам. Там же *Devices / Startup* — загрузка с диска.
2. **Ubuntu Server 24.04 LTS**, при установке — OpenSSH. Сервер — в той же сети, что камеры
   (192.168.1.239 и .240): проверка — `ping 192.168.1.239`. IP сервера лучше закрепить
   на роутере (DHCP-резервирование), чтобы адрес веба не менялся.
3. Docker и проект:

   ```bash
   sudo apt update && sudo apt install -y docker.io docker-compose-v2 git
   sudo usermod -aG docker $USER && newgrp docker
   sudo git clone https://github.com/TheCoree/track-seeds /opt/track-seeds
   sudo chown -R $USER: /opt/track-seeds && cd /opt/track-seeds
   ```

4. **Настройки с ПК** — пароли камер, ntfy, фразы, динамики, свои эталоны (в git их нет):

   ```bash
   # на ПК, из папки проекта:
   scp -r config user@сервер:/opt/track-seeds/
   ```

   Без копирования тоже можно — после запуска задать пароль камер:
   `docker compose run --rm -it track-seeds track-seeds password`; ntfy — в вебе.
5. **Запуск:** `./deploy/setup.sh`. Скрипт включает автозапуск Docker, открывает веб в
   локальную сеть (`WEB_HOST=0.0.0.0`), придумывает пароль на вход (покажет и сохранит в
   `.env`), собирает образ (первый раз — минут 10–15, нужен интернет) и ждёт запуска.
   Потом — проверка: `docker compose run --rm track-seeds track-seeds check`.

**Сам поднимается.** После перезагрузки или пропадания питания: BIOS включает компьютер →
Docker стартует со системой → контейнер (`restart: always`) — тоже; камеры переподключаются
сами. После падения процесса Docker перезапускает его. Настройки и журнал пишутся атомарно —
внезапное выключение их не портит.

**Доступ из локальной сети:** `http://IP-сервера:8080/`, логин `admin`, пароль из
`.env` (`WEB_PASSWORD`). Адреса не из локальной сети (`WEB_ALLOWED_NETWORKS`, по умолчанию 10/8,
172.16/12, 192.168/16) получают отказ, даже если порт пробросят наружу; если включён ufw — скрипт
открывает порт только для них. Из интернета — по домену и HTTPS, раздел «Доступ из интернета».

**Обновление** — одна команда, с доменом и без:

```bash
cd /opt/track-seeds && git pull && ./deploy/setup.sh
```

`config/`, `.env`, журнал событий, отчёты, аккаунты и сертификаты не трогаются. Пока собирается
новый образ, работает прежний; перерыв — секунды на пересоздание контейнера. **Состояние дробилок
продолжается:** сервер раз в 5 секунд и при остановке записывает уровень, работу привода и «с какого
времени» в `data/resume.json` и после запуска продолжает с них — «семена есть уже 2 ч», а не
«1 секунду»; тревога о том же не повторяется, напоминания идут по прежнему расписанию. Если за
перерыв что-то изменилось, кадры подтвердят это за обычные 5–10 секунд и придёт уведомление.
Перерыв дольше 15 минут (сервер был выключен) — неизвестно, что было, наблюдение начинается заново.

Логи — `docker compose logs -f --tail 100` (Caddy — `docker compose logs caddy`), нагрузка — `docker stats`.

## Клиенты

**Пригласить:** «Клиенты» → «Пригласить» → кого → срок (час … неделя) → «Создать ссылку» →
отправить в мессенджер. По ссылке регистрируется **один** человек (имя, логин, пароль), потом
она гаснет. Там же: отключить доступ (сразу, вместе с открытым видео и виджетом), выйти на всех
устройствах, ссылка для нового пароля, удалить; журнал входов за 180 дней.

**Что видит клиент:** обзор и страницы дробилок (камера «Зоны» / «Оригинал», состояние,
графики за 15 минут), события (без проверок оповещений и без доставки уведомлений), отчёты,
«Мой аккаунт». Настройки и `/api/meta`, `/api/settings`, эталоны, динамики — отказ 403.

**Отчёты** (у разработчика тоже): день — лента суток по состояниям и список простоев; неделя
и месяц — часы по дням. Плитки: работала (вместе с «без зерна»), стояла и сколько раз
остановилась, крутилась без зерна, нет связи / данных; первый запуск, последняя остановка,
дольше всего без остановки. «Показать таблицей», «Скачать CSV» (открывается в Excel).
Сервер раз в 5 секунд записывает состояние каждой дробилки в `data/worklog.db` (хранится
400 дней); пока сервер выключен — «нет данных». Остановки и «без зерна» короче минуты не
считаются; остановка — когда перед ней дробилка работала (а не «сервер включили, а она стоит»).

**Приложение на телефон (PWA):** iPhone — Safari → «Поделиться» → «На экран „Домой“»; Android —
Chrome → «Установить приложение» (или кнопка в «Мой аккаунт»). Полностью (service worker:
мгновенный запуск, без связи — «нет связи», а не пустой экран) — только по HTTPS.

**Виджет iPhone и iPad:** «Мой аккаунт» → «Создать виджет» → скрипт с ключом (показывается один раз) →
Scriptable → «+» → вставить; на экране «Домой» добавить виджет Scriptable и выбрать скрипт.
Размеры: малый (состояние), средний (плитки и полоса суток), большой (кадры камер и итоги дня),
очень большой — на iPad (крупные кадры, сутки под каждым), экран блокировки (круглый, прямоугольный,
строкой). Вид — как у системных виджетов: цвета и шрифт iOS, значки SF Symbols, тёмная тема; размеры
плиток и кадров рассчитываются под экран устройства — ничего не вылезает. Нажатие на плитку открывает
дробилку на сайте. Ключ — только чтение `/api/widget`, отзывается там же. Работает с мобильного
интернета, если задан `WEB_PUBLIC_URL`.

### Доступ из интернета (домен и HTTPS)

**Один раз:**

1. У регистратора домена — **A-запись** `seeds.example.ru` → внешний IP (у провайдера он должен
   быть постоянным — «белый статический IP»).
2. На роутере — **проброс портов 80 и 443** (TCP; 443 ещё и UDP) на IP сервера. Порт 8080 наружу
   **не** пробрасывать.
3. В `.env` на сервере: `DOMAIN=seeds.example.ru` → `./deploy/setup.sh`.

Скрипт включает Caddy (`deploy/Caddyfile`, сервис `caddy` в `docker-compose.yml`, профиль `domain`:
пишет `COMPOSE_PROFILES=domain` в `.env`, поэтому и простой `docker compose up -d` поднимает его),
ставит `WEB_PUBLIC_URL=https://…` (ссылки-приглашения, виджет) и `WEB_ALLOWED_NETWORKS=any`, открывает
80 и 443 в ufw и проверяет HTTPS. Сертификат Let's Encrypt Caddy получает и продлевает сам,
хранит в томе `caddy-data` — обновления его не трогают. Caddy ставится из Debian в тот же образ, что и
сайт (сервис `caddy` запускается из `track-seeds:latest`): Docker Hub с сервера бывает недоступен, а apt
работает. Обновлять — так же, `git pull && ./deploy/setup.sh`. Убрать домен — стереть `DOMAIN` и снова
запустить скрипт.

**Что видно из интернета:** только сайт по `https://` — вход, страницы дробилок, кадры и видео для
вошедших. Камеры, их адреса и пароли наружу не попадают: к камерам ходит только сервер внутри сети,
клиенту API отдаёт состояние без адресов камер. Напрямую на порт 8080 из интернета сервер не пускает
даже с `any` — только через Caddy (иначе пароль шёл бы без шифрования).

**Панель разработчика снаружи не открывается:** Caddy работает в сети хоста и передаёт настоящий адрес
посетителя в `X-Forwarded-For` (`WEB_TRUSTED_PROXIES`, по умолчанию 127.0.0.1; подделанный посетителем
заголовок Caddy заменяет), а вход admin работает только из `WEB_ADMIN_NETWORKS` (по умолчанию локальная
сеть) — пароль разработчика снаружи даже не проверяется. Из офиса — `http://IP-сервера:8080/`, из дома —
через SSH: `ssh -L 8080:127.0.0.1:8080 user@seeds.example.ru` (нужен проброс порта SSH) и в браузере
`http://127.0.0.1:8080/`.

**Через роутер Netcraze / Keenetic (KeenDNS)** — без белого IP и проброса портов: домен вида
`srv.имя.netcraze.link` указывает на облако Netcraze, HTTPS держит роутер. В роутере: «Сетевые правила» →
«Доменное имя» → «Веб-доступ к устройствам домашней сети» → правило: имя `srv`, устройство — сервер,
порт **8080**, протокол **HTTP**, доступ без авторизации роутера (вход — на сайте). В `.env`:
`DOMAIN=srv.имя.netcraze.link` → `./deploy/setup.sh`. Скрипт узнаёт KeenDNS по имени (или `DOMAIN_VIA=router`),
Caddy не включает, а адрес роутера пишет в `WEB_EXTERNAL_PROXIES`: роутер стоит в локальной сети, но всё,
что приходит через него, — из интернета. Без этого посетители из интернета выглядели бы как роутер,
то есть «локальная сеть», и им открылась бы панель разработчика. 502 на домене — роутер не достучался до
сайта: не тот порт или протокол HTTPS вместо HTTP.

Без своего IP и проброса портов можно и **Cloudflare Tunnel** (домен в Cloudflare): `cloudflared tunnel` на
сервере → `http://127.0.0.1:8080`, в `.env` — `WEB_ALLOWED_NETWORKS=any` и `WEB_PUBLIC_URL`, `DOMAIN` не задавать.

## 3. Работа сервера

- Веб: `WEB_HOST=127.0.0.1` — только с самого компьютера; `0.0.0.0` (так ставит
  `deploy/setup.sh`) — из локальной сети и только с разработчиком (`WEB_PASSWORD` или
  `track-seeds admin`, иначе сервер не запустится); чужие сети отсекаются по `WEB_ALLOWED_NETWORKS`.
- Без браузера:

| Команда | Что делает |
|---|---|
| `track-seeds crushers` | дробилки: камера, зоны, эталоны, динамики, есть ли пароль |
| `track-seeds password [id]` | задать пароль камеры (спросит в терминале; без id — обеим) |
| `track-seeds check [id]` | проверить камеры, зону желоба на текущем кадре, движение привода, динамики (без звука), голос, ntfy |
| `track-seeds say "текст" --crusher id` | сказать фразу на динамиках дробилки — проверить звук |
| `track-seeds admin [логин]` | завести разработчика или сменить ему пароль (спросит в терминале); `--no-2fa` — телефон с кодами потерян |
| `track-seeds users` | аккаунты: разработчики и клиенты, 2FA, устройства, когда заходили |

  В Docker — `docker compose run --rm track-seeds track-seeds …` (для `password` и `admin` — с `-it`).
- Забыли пароль admin — смените `WEB_PASSWORD` в `.env` и перезапустите: пароль admin станет этим,
  его сессии закроются.
- `GET /api/health` — для мониторинга (без входа; 503, если встала шина событий; подробности —
  только из локальной сети).
- При остановке сервер досылает уведомления из очереди и договаривает фразу (до 60 с).
- Испорченный `config/crushers/<id>/settings.json` дробилку не останавливает: она работает
  с настройками из программы, ошибка видна на вкладке «Камера» и в `track-seeds crushers`.

### Поправить зону или камеру

Зоны и адреса камер — в `src/track_seeds/crushers.py` (углы в пикселях кадра 2560×1440),
вшитые эталоны — в `src/track_seeds/builtin/<id>/samples/`. После правки — пересобрать образ.
Если у камеры сменился IP, можно не ждать: вкладка «Камера» → адрес → «Сохранить»
(хранится в `config/`, «Вернуть» — адрес из программы).

### Физический динамик у сервера

Тип динамика «Динамик у сервера». Звук идёт через ALSA (`aplay`). В `docker-compose.yml`
раскомментируйте `devices: /dev/snd` и `group_add` (номер группы: `getent group audio | cut -d: -f3`).
Если звука нет: `aplay -l` на сервере покажет карты — впишите устройство, например
`plughw:1,0`; проверка — `track-seeds say "Проверка" --crusher drobilka-1`.

### Динамик камеры Hikvision

Звук передаётся как «двусторонний звук» (ISAPI TwoWayAudio). В камере: *Конфигурация →
Видео/Аудио → Аудио*, кодек **G.711ulaw** (или alaw); пользователю нужно право на
двусторонний звук. Одна камера-динамик может быть у обеих дробилок — фразы идут по
очереди. При неверном пароле повторов нет (иначе камера заблокирует IP).

## Безопасность

- Пароли камер и динамиков — в `secrets.json` (права 600), отдельно от настроек; API их не
  отдаёт.
- Камера с логином, но без пароля не подключается — иначе повторные неверные входы
  заблокировали бы IP; динамик без пароля камеру не трогает.
- Веб: только из `WEB_ALLOWED_NETWORKS` (по умолчанию локальная сеть); без входа — только с
  этого компьютера и пока разработчик не заведён.
- Вход: логин и пароль (scrypt) → access-токен (JWT HS256, 15 минут) и refresh-токен (90 дней
  у клиента, 7 — у разработчика; продлевается, пока сессией пользуются) в cookie `HttpOnly`,
  `SameSite=Strict`, по HTTPS — `Secure`. Refresh меняется при каждом обновлении; старый,
  предъявленный повторно, закрывает сессию (кража). Роль и блокировка берутся из базы на каждый
  запрос — отключённый клиент теряет доступ сразу, открытое видео обрывается за 10 с.
- Перебор: неверный пароль — пауза 1 с; с одного адреса — не больше 10 ошибок за 15 минут, на
  один логин — 30; несуществующий логин проверяется так же долго, как настоящий.
- Разработчик: только из `WEB_ADMIN_NETWORKS`; снаружи его пароль даже не проверяется. Вход по
  коду (TOTP: Яндекс Ключ, Google Authenticator) — «Мой аккаунт» → «Вход по коду»; QR рисует сам
  сервер. Включение закрывает остальные сессии.
- Каждый маршрут API — в роутере «без входа» / «вошедшие» / «разработчик»; тест проверяет, что
  без входа отвечают только вход, регистрация и `/api/health`.
- Изменяющие запросы требуют заголовок `X-Track-Seeds` (чужая страница не отправит — CSRF);
  заголовки `CSP`, `X-Frame-Options: DENY`, `nosniff`, `Permissions-Policy`, `COOP/CORP`,
  по HTTPS — `HSTS`; ответы API — `Cache-Control: no-store`.
- Загрузка эталона — до 20 МБ, только JPEG/PNG с пропорциями камеры. Вшитые эталоны не
  удаляются и не переотмечаются из интерфейса.
- Запись файлов — атомарная с `.bak`.
- Docker: не root, `network_mode: host` без открытых наружу портов (веб на 127.0.0.1).
- Из интернета (`WEB_ALLOWED_NETWORKS=any`) — только через обратный прокси на этом сервере (Caddy, HTTPS);
  напрямую на порт сайта — только из локальной сети. Caddy получает из `.env` лишь домен и порт.

## Как определяется «семена закончились»

Дважды в секунду зона выпрямляется и сравнивается с эталонами по текстуре (локальные бинарные
шаблоны — зерно даёт мелкую «рябь», металл гладкий; почти не зависит от яркости), силе
перепадов, распределению яркости и цвету (в ИК-режиме цвет не используется). Ближе к эталону
«есть» — оценка к 1, к «пусто» — к 0.

Защита от ложных тревог:
- «закончились» — только если зона пуста **всё время** «Закончились, если пусто дольше»
  (5 с, ~10 проверок): окно делится на три части, и в каждой ≥70 % кадров должны показывать «пусто»;
- кадры, где зону закрывает человек, где слишком темно или картинка не похожа ни на один
  эталон (крышка, сдвиг камеры), **не голосуют**; людей режим не отслеживает и не рисует —
  детектор нужен только для этой проверки. Он дорогой (~0.2 с процессора на кадр), поэтому
  запускается, только когда кадр может что-то изменить (желоб «пусто», привод не в своём
  состоянии), и не чаще раза в секунду; в обычной работе проверка стоит ~3 мс;
- если зону не видно дольше 5 мин — отдельное «не видно желоб», а не «закончились»;
- после смены настроек состояние сохраняется — тревога не повторяется.

**Работает ли дробилка** — по зоне «привод»: при каждой проверке считается доля зоны, которая
изменилась с прошлой проверки (общая смена яркости выравнивается). Больше порога (5 %) —
крутится. «Стоит» — если привод неподвижен 10 с, «работает» — если движется 5 с. Пока стоит:
уведомление «Дробилка остановилась» (на телефон с высокой важностью, всплывающее сообщение со
звуком в браузере, голосом — если задана фраза), ни «закончились», ни напоминаний, ни
«не видно желоб». После запуска семена подтверждаются заново по кадрам в работе: запустили
пустую — «закончились» через 5 + 5 с; запустили с семенами — «Дробилка снова работает».
Выключатель «Сообщать, когда дробилка остановилась и запустилась» на вкладке «Оповещения»;
если дробилка уже стояла при запуске сервера — только запись в журнал. Кадры, где привод
в эту секунду не движется, в «пусто» не идут ещё до подтверждения «стоит»: лопасть, замершая
перед зоной при остановке, тревогу не поднимет. На двух
дробилках: крутящийся привод — 16–32 % зоны за полсекунды, неподвижные участки кадра — до 1 %.

**Уверенность в интерфейсе.** Оценка зоны — отношение расстояний до эталонов «есть» и
«пусто»: кадр, явно похожий на семена, даёт 0.85–0.95, хотя сомнений нет. Для показа она
пересчитывается в уверенность с той же границей (50 %), но без «серой середины»: отношение
шансов относительно границы в 4-й степени. Решения по-прежнему принимаются по оценке —
меняется только то, что видит человек. На обеих дробилках при полном желобе — 99,9–100 %.

Проверено: на 56 парах реальных фото (семечки, пшеница, рожь, ячмень × оцинковка,
нержавейка, рифлёный лист, фанера) — 0 ошибок на кадр при обычном освещении и ~2 % при
резкой смене света; в сценарии «полный → убывает → пусто → ночь → досыпали» с проходящими
людьми — ровно нужные события без ложных тревог; на живой офисной камере 10 минут — ни одной
ложной тревоги даже с одним эталоном «есть».

## Уведомления ntfy

В веб-интерфейсе: «Уведомления и голос» → ntfy (сервер, топик, токен) → «Отправить тест».
У каждого события в журнале видно, куда оно доставлено и с какой ошибкой, если нет.

**Быстрый вариант — публичный ntfy.sh** (для разработки):

1. Поставьте приложение ntfy ([Android](https://play.google.com/store/apps/details?id=io.heckel.ntfy) /
   [iOS](https://apps.apple.com/app/ntfy/id1625396347)) или откройте https://ntfy.sh/app.
2. «+» → *Subscribe to topic* → введите значение `NTFY_TOPIC` из `.env`, сервер оставьте ntfy.sh.
3. В `.env`: `NOTIFY_CHANNELS=log,ntfy`, затем `make notify-test`.

Топик на ntfy.sh — это фактически пароль: кто знает имя, тот читает уведомления
и снимки. Поэтому имя длинное и случайное (`python3 -c "import secrets; print(secrets.token_urlsafe(16))"`).

**Для прода — свой сервер ntfy** с авторизацией, чтобы снимки со склада не шли
через чужой сервер. Минимальный `server.yml`:

```yaml
base-url: "https://ntfy.example.ru"        # адрес, по которому телефон достучится до сервера
cache-file: "/var/cache/ntfy/cache.db"
attachment-cache-dir: "/var/cache/ntfy/attachments"   # без этого снимки не прикладываются
auth-file: "/var/lib/ntfy/user.db"
auth-default-access: "deny-all"
upstream-base-url: "https://ntfy.sh"       # нужно для мгновенных пушей на iOS
```

```bash
ntfy user add --role=admin me              # для телефона
ntfy user add seeds                        # для track-seeds
ntfy access seeds 'seeds-*' write-only
ntfy token add seeds                       # → tk_..., положить в NTFY_TOKEN
```

В `.env`: `NTFY_URL=https://ntfy.example.ru`, `NTFY_TOKEN=tk_...`. В приложении
добавьте сервер и войдите под `me`. Если на сервере не настроены вложения,
уведомление всё равно придёт, только текстом без снимка.

## Если камера не подключается

- `ping <ip>` и `nc -vz <ip> 554` — доступность и порт RTSP;
- Hikvision: `rtsp://IP:554/Streaming/Channels/102` (`101` — основной поток, `102` — субпоток;
  на регистраторе камера 3 → `301`/`302`); Dahua: `…/cam/realmonitor?channel=1&subtype=1`;
- лучше отдельный пользователь камеры: тип «Оператор», право «Удалённый: просмотр»;
- **после нескольких неверных паролей Hikvision блокирует IP на ~30 мин** — проверяйте
  кнопкой «Проверить подключение» или `track-seeds check`;
- `ffplay "rtsp://…"` — если не играет и там, проблема не в программе; камера без RTSP по TCP —
  «Транспорт RTSP: UDP».

## Старые режимы (люди, номера машин)

Остались для отдельного запуска без веба: `track-seeds run` с камерой из `.env`
(`ANALYZERS=presence` или `plates`), команды `check-camera`, `detect`, `plates`, `vehicles`.
К дробилкам не относятся.

### Люди в кадре (`presence`)

YOLOX (Apache-2.0) через OpenCV DNN; в OpenCV 5 HOG-детектора больше нет.
Детекция идёт 2 раза в секунду (`PRESENCE_INTERVAL_S`).

Сеть сжимает кадр до 416×416, и на широкоугольной камере сидящие или далёкие люди
становятся слишком мелкими. Поэтому при `DETECTOR_TILING=true` детектор прогоняется
по целому кадру и по двум квадратным половинам, результаты сливаются (≈70 мс на кадр
1280×720 у `yolox_tiny` на CPU вместо ≈22 мс). Вложенные рамки одного человека
(«торс» внутри «человека») подавляются (`DETECTOR_CONTAINMENT`), чтобы не считать
его дважды. На реальных кадрах склада с двумя сидящими людьми правильное число
людей было в 17 из 23 кадров без нарезки и в 23 из 23 с нарезкой; `yolox_s` без
нарезки в той же сцене дал 12–22 из 23 при 85 мс на кадр.

Когда приходят уведомления (ограничения частоты нет, только смена состояния):

| Уведомление | Когда | Настройки |
|---|---|---|
| «человек в кадре» | в пустом кадре появились люди: `ENTER_HITS` детекций подряд (≈1 с) | `PRESENCE_ENTER_HITS` |
| «кто-то пришёл / ушёл» | число людей изменилось, но кадр не пуст: сглаженное (медиана за 5 с) новое число держится 10 с | `PRESENCE_COUNT_WINDOW_S`, `PRESENCE_COUNT_CHANGE_AFTER_S`, `PRESENCE_COUNT_CHANGES` |
| «человек ушёл» | ни одного человека `LEAVE_AFTER_S` секунд подряд | `PRESENCE_LEAVE_AFTER_S` |

Пока камера недоступна, уход не фиксируется.

Если много ложных срабатываний — поднимите `DETECTOR_CONFIDENCE` или
`PRESENCE_MIN_BOX_AREA`; если людей пропускает — опустите `DETECTOR_CONFIDENCE`
(0.35) или увеличьте `PRESENCE_LEAVE_AFTER_S`. Подбирать удобно через
`make detect` и `make preview` (в превью видно и сглаженное число, и число в кадре).

## Пресет «Номера машин» (`plates`)

```env
ANALYZERS=plates          # или presence,plates — если камера смотрит и на людей, и на машины
```

Как работает:

1. YOLOX находит машины (`car`, `truck`, `bus`, `motorcycle`), трекер сопоставляет
   их между кадрами. Проезжающие мимо машины игнорируются.
2. Машина «остановилась», если 3 с почти не сдвигалась (`PLATES_STOP_*`).
3. Пока стоит, на каждом кадре внутри её рамки ищется номерной знак
   ([open-image-models](https://github.com/ankandrew/open-image-models), YOLOv9) и читается
   ([fast-plate-ocr](https://github.com/ankandrew/fast-plate-ocr)); обе MIT, ONNX Runtime, ≈70 мс на машину.
4. Прочтение принимается, только если номер не уже `PLATES_MIN_PLATE_WIDTH` (80 px),
   каждый символ прочитан с уверенностью от `PLATES_MIN_CHAR_CONFIDENCE` (0.7) и текст
   приводится к формату российского номера (А123ВС 77, такси АВ123 77, полиция А1234 77,
   прицепы, мотоциклы). Ошибки вида «0» вместо «О» исправляются по позиции символа.
   Всё остальное отбрасывается: мелкий или размытый номер OCR «читает» как
   правдоподобный мусор, и лучше не прочитать ничего, чем прочитать неправильно.
5. Как только номер прочитан одинаково `PLATES_CONFIRM_READS` раз (по умолчанию 3,
   это ~1.5 с) — уведомление «подъехала машина С484НХ 70» с цветом, типом и снимком.
   Прочитан меньше раз за `PLATES_READ_TIMEOUT_S` — уведомление с пометкой «прочитан
   неуверенно». Не прочитан ни разу — машина пропускается молча (обычно это дальние
   стоящие машины); включить такие уведомления — `PLATES_NOTIFY_UNREADABLE=true`.
6. Машины не видно `PLATES_LEAVE_AFTER_S` (30 с) — «уехала, стояла 12 мин».
7. Если программу перезапустили, а машина так и стоит, заезд с тем же номером
   продолжается в журнале без повторного «подъехала».

Журнал — `data/vehicles.db` (SQLite) и снимки в `data/vehicles/ГГГГ-ММ-ДД/`
(кадр с рамками + отдельно вырезанный номер):

```bash
make vehicles                                  # последние 30 заездов
.venv/bin/track-seeds vehicles --plate 484     # поиск по части номера
.venv/bin/track-seeds vehicles --csv out.csv   # для Excel
```

Проверено:
- фото российских машин с Wikimedia Commons: 8 из 8 номеров прочитаны верно
  (С484НХ 70, К694ОВ 70 ×3, С497НН 70, С729ОВ 70, С071МВ 70, Т532ХР 72), цвет — 7 из 7;
- реальная камера во дворе (2560×1440): ближняя машина (номер ≈200 px) прочитана
  верно на 12 кадрах из 12, у дальних машин (номера 40–60 px) ложных прочтений 0 из 48;
- синтетическое видео «подъехала → стоит → уехала»: оба уведомления и запись в журнале.

Ограничения и советы:

- **Камера.** Номер должен занимать от ~80–100 px в ширину. На общем плане двора
  читаются только ближние машины — для въезда лучше отдельная камера у ворот/шлагбаума
  и основной поток (`.../101`). Проверка — `make plates`, когда машина в кадре.
- **Зона.** Если камера видит и въезд, и дальнюю стоянку, ограничьте поиск зоной
  `PLATES_ROI` (её рамка видна в `make preview`).
- **Ночь.** В ИК-режиме картинка чёрно-белая — цвет будет серый/белый; номер читается,
  если ИК-подсветка его не засвечивает (ночью не проверялось).
- **Цвет примерный:** по пикселям средней части кузова; блики, тени и грязь мешают.
  Варианты: белый, серебристый, серый, чёрный, бежевый, коричневый, красный,
  оранжевый, жёлтый, зелёный, голубой, синий, фиолетовый.
- **Иностранные номера** (Казахстан, Беларусь…) с `PLATES_FORMAT=ru` будут «прочитан
  неуверенно» или случайно совпадут с российским форматом; для смешанного потока —
  `PLATES_FORMAT=any`.
- Машины, уже стоящие в кадре при запуске, будут записаны как подъехавшие.
